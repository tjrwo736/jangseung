# 장승 0.3.1 릴리스 노트

hook 호출을 빠르게 한 릴리스입니다. 판정은 바뀌지 않았습니다.

```bash
python -m pip install --upgrade jangseung
```

Windows에서 `aeg install`로 등록했다면, 업데이트한 뒤 프로젝트에서 `aeg install`을 다시 실행하세요. 등록이 더 빠른 형태로 바뀌고, 상주 판정 프로세스(아래)를 쓰게 됩니다. 다시 실행하지 않아도 기존 등록은 그대로 동작하고 빨라집니다. 플러그인으로 쓰면 플러그인을 업데이트하세요.

## 얼마나 빨라졌나

같은 프로젝트에서 0.3.0과 0.3.1을 번갈아 240번씩 실행한 중앙값입니다(Windows 11, Python 3.14.5, 백신 실시간 검사 켜짐, Claude Code가 hook을 부르는 것과 같은 방식으로 프로세스를 새로 띄움, 패키지는 C: 드라이브).

| 실행 방식 | 0.3.0 | 0.3.1 | 변화 |
|---|---|---|---|
| Windows에서 `aeg install`을 다시 실행한 등록 (`python.exe -I -S …\jangseung\_hook.py hook-run`) | 150.7 ms (`aeg.exe`) | 32.7 ms | −78% |
| 같은 등록, 상주 판정을 끈 경우 (호출마다 판정) | 150.7 ms | 50.8 ms | −66% |
| 다시 실행하지 않은 기존 등록 (`aeg.exe hook-run`) | 150.7 ms | 86.4 ms | −43% |
| `python -I -m jangseung.cli hook-run` | 137.8 ms | 66.0 ms | −52% |
| 플러그인 hook | 276.1 ms | 79.5 ms | −71% |
| 플러그인, 상주 판정을 끈 경우 | 276.1 ms | 109.8 ms | −60% |

- 이 표를 잰 때 이 PC는 오전보다 느렸습니다. 같은 때 잰 맨 시작 시간은 작은 네이티브 프로그램 약 14 ms, Python 22.7 ms, Node.js 38.1 ms였고, 오전에는 각각 약 10 ms, 17.3 ms, 34.5 ms였습니다. 0.3.0과 0.3.1을 번갈아 재므로 비율은 그대로 비교할 수 있습니다.
- 다른 도구와 견주면: 이 PC에서 네이티브 실행 파일(dcg 등)은 프로그램 시작만으로 약 14 ms, Node.js 도구(cc-safety-net 등)는 38 ms보다 빠를 수 없습니다. 그 도구들 자체는 재지 않았습니다.
- 0.3.1 값은 모듈 캐시 파일과 상주 판정 프로세스가 준비된 뒤의 값입니다. 업데이트 뒤 첫 호출은 둘을 준비하느라 조금 더 걸립니다.
- 설치 파일이 놓인 지 얼마 안 됐을 때 잰 값은 각각 약 10 ms 높았습니다. 백신이 새로 쓴 파일을 더 검사하기 때문으로 보입니다(원인은 확인하지 않음).
- 플러그인의 0.3.0 값은 `python3`이 Microsoft Store 안내 프로그램인 이 PC에서 잰 것입니다. 진짜 `python3`가 있는 환경에서는 차이가 Python 시작 한 번(약 30 ms)만큼 작습니다.
- 플러그인 값에는 Git Bash 시작과 셸이 Python을 자식 프로세스로 띄우는 시간(합쳐 약 30 ms)이 들어 있습니다. 이 PC에서 플러그인이 고르는 `python3`는 Python 설치 관리자의 Python인데, 그 폴더에서는 파일 상태 확인 한 번이 `C:\Python314`보다 약 10배 느립니다(67 µs 대 5 µs).

## 바꾼 것

hook은 도구 호출마다 새 Python 프로세스로 실행됩니다. 그래서 프로세스를 띄우는 시간, 모듈을 불러오는 시간, 처음 한 번만 드는 비용이 매번 듭니다. 0.3.0의 한 호출은 Python 시작 약 30 ms, 모듈 불러오기 약 77 ms, 판정과 기록 약 20 ms였습니다.

상주 판정 프로세스 (Windows):

- **판정 코드를 불러 둔 프로세스가 답합니다.** 판정 자체는 약 5 ms인데, 호출마다 Python을 띄우고 모듈을 불러오는 데 그 몇 배가 들었습니다. 이제 hook 호출은 입력을 읽어 이름 있는 파이프로 상주 판정 프로세스에 넘기고, 받은 답을 그대로 씁니다. 같은 장승을 깨어 있게 둔 것이고, 다음 규칙을 지킵니다.
  - **같은 코드, 같은 시작.** 상주 프로세스는 hook 명령과 같은 실행기, 같은 Python, 같은 인터프리터 옵션으로 시작하고, 호출마다 판정하던 것과 같은 함수로 판정합니다.
  - **같은 입력.** 각 호출은 그 호출의 인자, 작업 폴더, 환경 변수 전체, 입력 바이트, 출력 인코딩으로 판정합니다. 한 판정이 남긴 것을 다음 판정이 읽지 않습니다. hook이 판정을 부르는 깊이만큼 재귀 한도도 맞춥니다.
  - **같은 파일.** 답하기 전마다 코드가 온 폴더와 `sys.path`의 폴더를 디스크와 비교합니다. 파일이 바뀌거나, 생기거나, 없어지거나, 모듈을 가릴 수 있는 폴더가 새로 생기면 답하지 않고 끝나며, 그 호출은 직접 판정합니다. 업그레이드나 코드 수정은 바로 다음 호출부터 반영됩니다.
  - **fail-closed.** 상주 프로세스가 없거나, 1초 안에 키를 가졌음을 증명하지 못하거나, 10초 안에 답하지 않거나, 답의 서명이 맞지 않으면 hook이 지금처럼 직접 판정합니다. 상주 프로세스를 끝내도 느려질 뿐 보호는 그대로입니다. 없거나 증명하지 못한 경우에는 새로 띄웁니다.
  - **기록.** ledger 기록은 판정이 남기며, 답보다 먼저 씁니다. hook이 기다리기를 포기한 호출은 판정하지 않아 기록이 두 번 남지 않게 합니다.
  - **로컬, 본인만.** 파이프는 원격 연결을 받지 않고 현재 사용자와 SYSTEM만 열 수 있습니다. hook은 먼저 도전값을 보내고, 상주 프로세스가 `%LOCALAPPDATA%\jangseung\resident`의 키로 증명해야 호출 내용을 보냅니다. 답은 그 호출 내용에 묶어 같은 키로 서명합니다.
- **쓰는 곳:** Windows에서 `jangseung/_hook.py`(새 등록)나 `aeg` 실행기(플러그인)로 시작한 `hook-run`. `aeg.exe`, `python -m`, Codex 등록, macOS·Linux는 호출마다 판정합니다.
- **수명:** 세션 시작 점검이 띄우므로 세션의 첫 도구 호출부터 빠릅니다. 15분 동안 호출이 없으면 스스로 끝납니다.
- **끄기:** hook 환경에 `JANGSEUNG_RESIDENT=off`를 두면 호출마다 판정합니다. Claude Code에서는 설정의 `env`에 넣을 수 있습니다.
- **보이는 것:** 작업 관리자에 `python.exe`가 하나 남습니다(창 없음, 약 30 MB). 실제 `claude -p` 세션 시간은 켬 7.1 s, 끔 6.9 s로 같았고, Claude Code는 이 프로세스를 기다리지 않았습니다.

프로세스 시작:

- **Windows `aeg install`은 Python을 직접 띄웁니다 (약 22 ms).** `aeg.exe`는 Python을 두 번째 프로세스로 띄우고, 가상환경의 `python.exe`는 진짜 Python을 세 번째 프로세스로 띄웁니다. 이제 `aeg install`은 Claude Code hook을 `<python.exe> -I -S <...>\jangseung\_hook.py hook-run`으로 등록합니다. 프로세스가 하나입니다.
  - 가상환경에 설치했으면 `_hook.py`가 `sys.prefix`를 그 가상환경으로 둡니다. 가상환경의 `python.exe`로 시작했을 때와 같습니다. 그래서 가상환경 안을 고치는 명령은 전처럼 장승 자신의 실행 폴더로 판정됩니다.
  - 패키지가 가상환경의 `Lib\site-packages`에 없을 때(편집 가능 설치 등), Python이 Microsoft Store 별칭일 때, 실행 파일 이름이 `python*.exe`가 아닐 때는 전처럼 `aeg.exe`로 등록합니다.
  - Codex hook과 macOS·Linux 등록은 바꾸지 않았습니다. Codex는 명령이 바뀐 hook을 `/hooks`에서 다시 승인할 때까지 끕니다.
- **site-packages를 읽지 않습니다 (`-S`, 약 3 ms).** 플러그인과 새 등록은 Python을 `-S`로 띄웁니다. site-packages와 `.pth` 파일을 처리하지 않고, 표준 라이브러리 뒤에 장승 패키지가 든 폴더만 더합니다.
- **답을 낸 뒤 바로 끝납니다 (약 3 ms).** `hook-run`과 `session-check`는 출력을 비운 뒤 `os._exit`로 끝납니다. 인터프리터가 모든 모듈과 객체를 정리하는 과정을 건너뜁니다. hook 경로는 열린 파일, 스레드, 종료 처리기를 남기지 않습니다. 표준 출력을 비우지 못하면 `hook-run`은 2(차단)로 끝납니다. 전에는 Python이 120으로 끝났습니다.

모듈 불러오기:

- **컴파일된 모듈을 파일 하나에서 읽습니다 (약 10~16 ms, Windows).** Python은 모듈마다 `__pycache__`의 컴파일 파일을 하나씩 엽니다. 백신 실시간 검사가 켜진 Windows에서는 파일을 한 번 여는 데 약 0.3 ms가 들고, hook은 표준 라이브러리를 포함해 약 60개 모듈을 불러옵니다. 이제 hook 프로세스는 불러온 모듈의 컴파일된 형태를 패키지 폴더의 `__pycache__/hook-run-imports.<버전>.bin` 파일 하나에 모아 두고, 다음 호출부터 그 파일 하나만 엽니다. 세션 시작 검사는 자기 파일(`session-check-imports.<버전>.bin`)을 따로 씁니다.
  - Windows에서만 씁니다. Linux(WSL Ubuntu, Python 3.14.4)에서 돌려 보니 파일 열기가 싸서 시간 차이가 없었으므로(캐시 없음 20.5 ms, 있음 20.7 ms), macOS와 Linux는 Python의 불러오기를 그대로 씁니다.
  - 바뀌는 것은 바이트를 어디서 읽느냐뿐입니다. Python은 전처럼 같은 경로를 같은 순서로 찾아 모듈을 고릅니다. 캐시에 든 형태는 머리말의 수정 시각과 크기가 소스 파일과 맞을 때만 쓰고, Python이 `__pycache__` 파일과 똑같이 다시 확인합니다. 맞지 않으면 `__pycache__` 파일을 읽거나 소스에서 다시 컴파일하고, 호출이 끝날 때 캐시 파일을 고쳐 씁니다.
  - hook 명령(`hook-run`, `session-check`)을 실행하려고 시작한 프로세스에서만 켜집니다. 패키지를 불러 쓰는 코드에는 영향이 없습니다. 캐시에서 무엇이 실패하든 보통의 불러오기가 그대로 동작합니다.
  - Python이 컴파일 파일을 쓰지 않도록 설정되어 있으면(`-B`, `PYTHONDONTWRITEBYTECODE`) 캐시 파일도 쓰지 않고, 이미 있는 파일은 읽습니다. `-I`로 시작하는 새 등록, `python -I -m`, 플러그인은 환경 변수를 보지 않으므로 항상 씁니다. Claude Code 2.1.316 CLI는 hook에 `PYTHONDONTWRITEBYTECODE`를 넘기지 않았습니다.
  - 패키지 폴더에 쓸 수 없으면 캐시 파일이 생기지 않고 전처럼 동작합니다.
  - 해시 기반 컴파일 파일(`SOURCE_DATE_EPOCH`를 두고 설치한 경우 등)은 캐시에 넣지 않고 늘 `__pycache__`에서 읽습니다.
  - 캐시 파일에는 검사합이 있습니다. 손상되었거나 8 MB보다 크거나 다른 Python이 쓴 파일은 무시하고 다시 씁니다. `-O`로 실행하면 이름이 다른 파일(`.opt-1`)을 씁니다.
  - 소스와 맞는 형태는 그 `__pycache__` 파일을 지워도 캐시에서 계속 읽습니다. 컴파일을 처음부터 다시 하게 하려면 패키지의 `__pycache__` 폴더를 지우세요. 캐시 파일도 그 안에 있습니다.
  - 캐시 파일은 옆의 `__pycache__` 파일처럼 코드를 담습니다. 장승은 자신이 실행되는 패키지 폴더 전체를 보호하므로 에이전트 명령은 이 파일에도 쓸 수 없습니다.
  - `pip uninstall`은 캐시 파일을 지우지 않습니다(설치 기록에 없는 파일이라서). 제거한 뒤 남은 `jangseung` 폴더는 지워도 됩니다.
- **캐시를 켜기 전에는 다른 모듈을 불러오지 않습니다.** `jangseung.cli.entry`는 `json`과 `__future__`를, 플러그인 실행기는 `pathlib`을 쓰지 않게 바꿨습니다. 새 등록과 플러그인에서 캐시를 켜기 전에 디스크에서 읽는 모듈은 패키지 자신의 네 개뿐입니다. `aeg.exe`는 pip가 만든 실행 스크립트가 `re`를 먼저 불러오므로 그만큼 덜 줄어듭니다.
- **`dataclasses`를 쓰지 않습니다 (약 25 ms).** `@dataclass`는 클래스마다 코드를 만들어 `exec`로 컴파일하고, 불러올 때 `inspect`도 함께 불러옵니다. hook이 쓰는 34개 클래스에서 약 25 ms였습니다. hook 경로는 같은 동작을 코드 생성 없이 주는 `jangseung.records`를 씁니다. 지원하지 않는 사용(상속, `ClassVar`, 다른 옵션)은 조용히 다르게 동작하지 않고 오류를 냅니다.
- **OpenSSL을 불러오지 않습니다 (약 4 ms).** SHA-256을 Python에 내장된 모듈에서 가져옵니다. 결과는 같습니다.
- **필요할 때만 불러옵니다 (약 3.5 ms).** `typing`은 타입 검사기만 읽게 했습니다. 한 번 허용, MCP 판정 모듈, `datetime`은 해당 호출에서만 불러옵니다. 기록의 시각은 `time`으로 `datetime`과 같은 글자로 씁니다.

판정과 기록:

- **경로를 판정 한 번에 한 번만 풉니다 (약 2 ms, Windows).** 한 판정이 프로젝트 루트와 장승 자신의 폴더 같은 몇 개 경로를 35번 풀었습니다. Windows에서는 한 번 풀 때마다 파일을 열어 약 0.1 ms가 듭니다. 이제 판정 하나 안에서 같은 경로는 한 번만 풀고 답을 다시 씁니다. 판정은 파일을 바꾸지 않으므로 답은 같습니다. 이 기억은 판정이 끝나면 사라지고 호출 사이에 이어지지 않습니다. 실패한 풀이는 기억하지 않습니다.
- **파일 이름 패턴을 정규식 없이 맞춥니다 (약 3 ms).** 기본 보호 목록의 패턴 약 90개를 프로세스마다 정규식으로 컴파일하던 것을, 같은 답을 주는 문자열 비교로 바꿨습니다. 모든 패턴에서 `fnmatchcase`와 답이 같은지 테스트합니다.
- **ledger 끝을 다시 읽지 않습니다 (약 4~6 ms, Windows).** 기록할 때마다 직전 기록을 읽어 사슬을 이었습니다. 방금 바뀐 파일을 읽으려고 열면 Windows 백신 검사가 먼저 돌아 약 4 ms가 걸렸습니다. 이제 기록한 뒤 마지막 기록의 번호와 해시, ledger의 크기와 수정 시각을 `.aeg/hook_ledger.head.*`라는 빈 파일의 이름에 적습니다. 다음 호출은 파일을 열지 않고 이름과 크기·시각만 확인합니다. 하나라도 다르면(다른 버전이 기록함, 복구, 보관, 끊긴 기록) 전처럼 읽어서 검사합니다.
- **입력을 64 KiB씩 읽습니다 (약 3 ms, Windows).** hook 입력을 한도(16 MiB)만큼 한 번에 읽으라고 하면 Windows가 16 MiB 버퍼를 준비하느라 호출마다 약 3 ms가 들었습니다. 이제 같은 한도까지 조각으로 읽습니다. 받는 바이트와 한도를 넘는 입력의 처리는 같습니다.
- **입력 디코딩 (약 1.7 ms).** BOM을 직접 떼고 UTF-8로 읽습니다. `utf-8-sig`와 결과가 같습니다.
- **플러그인은 Python을 한 번만 띄웁니다.** 0.3.0은 버전 확인용으로 `python3`를 한 번 더 실행했고, `python3`가 Microsoft Store 안내 프로그램이면 그 확인에만 약 110 ms가 걸렸습니다. 이제 셸이 PATH에서 `WindowsApps`가 아닌 `python3`를 고르고(없으면 `python`), 버전 확인은 실행기 안에서 합니다. 3.10보다 오래된 Python이면 실행기가 입력을 읽기 전에 종료 코드 97로 끝나고, 셸이 같은 입력을 `python`에 넘깁니다. 0.3.0과 같은 대체 순서입니다.

## 바꾸지 않은 것

- **판정.**
  - 테스트 파일의 문자열 3,818개로 만든 24,814개 호출(Bash, PowerShell, Read, Edit, Write, 네 가지 모드)을 정책이 없는 프로젝트와 있는 프로젝트에서 0.3.0과 0.3.1로 판정했습니다. 49,628개 모두 출력, 종료 코드, 사유 코드, 기록 항목, 입력 해시까지 같았습니다.
  - 실제 hook 프로세스로도 비교했습니다. 같은 호출 중 1,241개를 PyPI 0.3.0의 `aeg.exe`, 새 등록의 호출마다 판정, 새 등록의 상주 판정, 플러그인 실행기의 상주 판정, 새 `aeg.exe`로 각각 실행했습니다. 종료 코드, 표준 출력, 표준 오류가 모두 같았고 기록도 1,241건씩 남았습니다. 그 전에 414개로 모듈 캐시 있음과 없음도 비교했습니다.
- **Codex hook, macOS·Linux 등록 형태.**
- **Python 시작 시간.** 상주 판정으로 답한 호출 약 33 ms 가운데 약 23 ms는 Python 자체의 시작(같은 때 측정), 약 2 ms는 hook이 불러오는 장승 모듈 네 개, 약 6 ms는 상주 프로세스의 판정과 기록입니다. 네이티브 도구와의 차이는 프로그램 시작 시간의 차이(약 14 ms 대 23 ms)와 판정 시간입니다.

## 새 잔여 위험

- **RR-16:** ledger 끝을 표시 파일 이름에서 가져오므로, 바이트를 바꾸고 수정 시각을 되돌린 편집은 기록하는 순간에는 잡히지 않습니다. `aeg evidence verify-hooks`가 사슬 끊김으로 보고합니다. 에이전트는 `.aeg/`에 쓸 수 없고, 해시를 다시 계산한 변조는 전에도 기록 시점에 잡지 못했습니다.
- **RR-17:** 같은 사용자 권한으로 임의 코드를 실행할 수 있으면 상주 판정 프로세스를 흉내 낼 수 있습니다(키 파일을 읽거나 바꿔서). 그 권한이면 지금도 장승의 코드나 설정을 바꿀 수 있습니다. 다른 사용자는 파이프를 열 수 없고, 키를 증명하지 못하는 상대에게는 호출 내용을 보내지 않습니다.
- **RR-18:** 상주 프로세스가 키를 증명한 뒤 10초 안에 답하지 않으면 hook이 직접 판정합니다. 그 사이 상주 프로세스가 판정을 마치면 같은 호출의 기록이 두 건 남을 수 있습니다. 판정은 ledger 잠금을 최대 1초 기다리므로 정상 동작에서는 생기지 않습니다.

[잔여 위험 등록부](residual_risk.md)에 적었습니다.

## 확인 결과

- 자동 테스트: Windows, Python 3.14에서 1939 passed, 20 skipped. 새 테스트는 `tests/test_hook_speed_0_3_1.py`, `tests/test_hook_speed_0_3_1_start.py`, `tests/test_hook_import_cache.py`, `tests/test_resident.py`입니다.
  - 상주 판정: 실제 hook 프로세스로 띄우고 답하게 해서 다음을 봅니다.
    - 세 가지 모드의 여러 도구 호출, 잘못된 입력, BOM, 하위 작업 폴더, `CDPATH`, `--ensure-state`, Codex, 잘못된 옵션, 깊게 중첩된 입력에서 직접 판정과 바이트 단위로 같은지.
    - 코드나 새 패키지 폴더가 생기면 답하지 않고 끝나는지.
    - 키 없는 파이프에는 도전값 외에 아무것도 보내지 않고 새 프로세스로 바꾸는지.
    - 멈춘 프로세스는 약 1초 만에 직접 판정으로 넘어가고 새로 띄우는지.
    - 남은 키의 프로세스 번호가 다른 프로세스에 재사용된 경우를 세션 시작에서 바로잡는지.

    - 프로젝트 폴더를 붙잡지 않는지, `hook-run` 외에는 답하지 않는지, 유휴 종료.
